# 悬而未决的决定

[English](OPEN-QUESTIONS.en.md) | 简体中文

更新:2026-11-01。这里只列**需要产品/安全取向决定**的事,以及不定时的后果。工程侧仍在推进的部分不在此列。

## 1. iOS 的 ATS 策略

**现状**:客户端**没有做任何 ATS 配置**(`project.yml` 里 `GENERATE_INFOPLIST_FILE: YES`,没有 `NSAppTransportSecurity` 键),也就是走系统默认:只允许 HTTPS 加系统内置的少数例外。真实源验证中没有站点被拦,**因为已验证的源都用 https**;不能据此推断 http 源可用 —— 那种情况现在会直接失败,而且失败信息是系统的 ATS 报错。

**为什么要你定**:`NSAllowsArbitraryLoads` 一次放开最省事,代价是**整个 App 的网络都失去系统的最低保证**,包括与 AI 供应商的对话。按域例外更安全,但每遇到一个新源就要发一次版本。

**可选项**:A. 全局放开;B. 只给漫画源域名列表开例外(需要维护);C. 保持现状,遇到拦截再评估。**不定时的后果**:一旦真实用户遇到 http 站点,表现是“图不显示”,而不是可读的错误。

## 2. Cookie 从「全局」迁到「按源分区」

**现状**:每个源独立分区,这是安全设计的一部分;`.venera` 备份里的 cookie 是全局的,导入时目前只落地源与书架数据,**cookie 不迁移**。

**为什么要你定**:迁移意味着要把一份全局 cookie 复制进**多个**分区,这是“扩大凭据可见范围”的动作,默认做与不做都有代价。

**已定(2026-10-31,用户选择此方向)**:Core 给出目标分区,由客户端写入,不重建共享 jar。

- `backup.CookieTargets(备份源, 已装源)`:取备份自己带的源 —— 导入会把它们装上;"本机已装"不能当条件,新设备上什么都没装。备份不带源脚本时退化为所有已装分区。
- 分发本身由客户端做:每个目标分区各自写入(客户端按自己的分区命名规则加前缀,iOS 与桌面端都是 `comic:<key>`)。不按源筛选,因为 jar 只在域名匹配时送出,送给不访问该域的源等于没送。
- `PlanBackup` 因此多返回一个 `cookieTargets`;客户端据此把 cookie 写进各自的分区,不再有全局 jar。
- 三类行直接丢弃:没名字、没值、域名不是主机(含写入 `https://` 的脏数据)。

**仍未定的只剩**:导入时是否**默认勾选** cookie。当前 Core 的默认选择仍是不恢复(Cookie 属敏感数据),客户端要不要把它做成默认开启,是产品判断。

## 3. 视频播放架构(Windows/Linux)

**现状**:Core 有视频源与 HLS 解析,桌面端只接了阅读器;`browser.Sniffer` 明确返回不支持。

**为什么要你定**:播放要么交给 WebView(与阅读器同一套机制,能力受限),要么内嵌原生播放器(平台工作量翻倍,DRM/编码问题各不相同)。

**可选项**:A. WebView + `<video>`;B. 原生播放器(每平台一套);C. 只做“嗅探出直链,交给系统播放器”。**不定时的后果**:视频源能装、能搜,点开没反应。

## 4. 供应商包从哪来

**现状**:iOS 客户端能安装**文件夹或 zip/tar.gz**;Core 仓库里没有随附的供应商包。社区包 15 个样本中,只有原始 Copilot 与 `cloudflare-workers-ai` 能跑,其余卡在 Node 运行时。

**为什么要你定**:要不要随 Core 发布 1–2 个「纯 Web 能力」的参考包(例如 OpenAI 兼容、Anthropic 兼容),决定了用户装完 App 之后**是否有东西可用**。

**可选项**:A. 随 Core 发布参考包并内置进 App;B. 只写文档与模板,让用户自己找;C. 与社区协商,挑选能跑的包做推荐列表。**不定时的后果**:App 装好是空的,用户必须自己找到并安装第三方包才能用 AI 功能。

## 6. `enableTagsTranslate` 指的是什么

**现状**:4 个源把 `enableTagsTranslate: true` 写在声明里(`ehentai`、`hitomi`、`lanraragi`、`nhentai`),另有若干个写 `false`。**客户端从未读过这个字段**,所以标签一律按源给的原文显示。仓库里没有任何地方定义它的语义:源脚本不解释,Core 的文档与 `init.js` 也没有对应实现。

**为什么要你定**:能推断出的做法至少有两种,后果不同 ——
A. **用源自己的 `translation` 表翻译标签**:可立即实现,但那张表里主要是**分组名**(`Tags` → `标签`),不是标签值,翻译覆盖率会很低;
B. **接一份标签词典**(Venera 上游那种 tag → 本地语言的大表):覆盖率高,但要决定**词典从哪来、谁维护、是否随包分发**,以及字典缺失时是否显示原文。

两种都需要决定:**只影响显示,还是也影响搜索**(把中文标签翻译回英文再搜,会改变送到源的关键词)。

**不定时的后果**:现在什么都不发生 —— 用户看到的是源原文标签,不会出错,只是没被翻译。

## 5. 真实供应商账号的验证

**现状**:Core 侧的设备码、密钥、刷新、用量、模型、流式与取消都有测试,且用**真实 Copilot 包**跑过(假服务)。客户端侧的登录 UI、Keychain、传输也已通过 macOS 上的类型检查与单元测试。

**缺的是什么**:一次**真实账号 + 真实设备**的端到端验证。这一步需要你提供账号或亲自在设备上点一次。**不定时的后果**:可以说“实现完成”,但不能说“真的能用”;社区包的真实行为(限流、二次验证、地区限制)仍未知。

## 7. `magpieplugin.Sender` 目前没有生产调用方

**现状**:`Sender`(端点轮询、重试判决、`Pin` 钉住)有一整套测试,但**仓库里没有任何生产代码调用它**:`mobile` 的聊天走的是插件包自己的 `Host.HTTP`,桌面端直接对接 Magpie 桌面应用、不经过 `magpieplugin`。也就是说,重试判决与钉住在今天是**可用于宿主的库接口**,不是正在生效的保护。

**为什么要你定**:三种走向,代价不同 ——
A. **让 `mobile` 在有多个端点时用 `Sender`**(插件包声明镜像地址或备用账号时),这条路要改包的接口约定;
B. **只在桌面端的 Magpie 网关里用**(它确实在路由),那就要在桌面仓库接;
C. **保留为库接口并如实标注**,直到有调用方。现在的文档就是这么写的。

**不定时的后果**:不会出错,但也不能说「重试被约束住了」——那只是有测试的代码。
