# iOS AI 分层取舍:标准 API 与 Magpie 插件

[English](AI-CORE-BOUNDARY.en.md) | 简体中文

本文对照用户的新方案与此前的 Core 路由原型,用于决定后续实现边界。本轮只核查代码和修改文档,没有增加 API、删除原型或改动客户端实现。桌面 Nekophage 继续连接本机已安装的 Magpie;此处讨论 iOS 在 App 内独立运行的方案。

## 建议结论

采用用户提出的“标准 API 内置、扩展功能插件化”,同时把必要的执行机制留在 Core。Core 提供协议、插件宿主和调用扩展的入口,具体路由策略、供应商用量查询、内容脱敏等由插件实现。这样即使没有安装扩展插件,用户仍可用 API Key 调用 OpenAI/Anthropic 标准接口。

此前新增 `magpierouting` 与 `mobile.Magpie.PlanRoute` 是硬编码策略原型,不是已经兼容 Magpie 路由插件的宿主。不要继续把它扩大为必经的内置调度器。保留现有源码与测试供后续拆分参考;若要移除导出方法或文件,再单独处理兼容与删除确认。

## 三种方案的取舍

| 方案 | 优点 | 主要代价 | 适用性 |
|---|---|---|---|
| 此前:Core 内置供应商与完整调度 | 一套实现可测,不装插件也有复杂策略 | 套餐、优先级、脱敏、统计等业务变化都推动 Core/框架/App 更新,Core 越来越像整套 Magpie | 不建议继续扩大 |
| 极端插件化:连协议与执行规则都交给插件 | 可替换面最大 | 标准调用依赖装包;每个插件可能各自处理流、取消和凭据,容易行为漂移 | 不建议 |
| 建议:标准协议和执行底座内置,策略与扩展装插件 | 标准 API 开箱可用,扩展按需安装;共享机制统一 | 要先做明确的插件接口、生命周期与错误规则,不能只把函数搬进 JS | 最符合用户目标 |

插件化减少后续业务耦合,不代表首次实现更省:路由/中间件/用量观察接口目前未接齐。也不能承诺每次插件更新都无须更新宿主;新能力可能需要新的宿主 API 版本。

## Core 要内置哪些内容

| 内容 | 保留在 Core 的原因 | 当前真实状态 |
|---|---|---|
| OpenAI Chat Completions / Responses、Anthropic Messages | 原生协议适配不应依赖下载供应商插件 | 有基本请求编码与 SSE 解析,还没有独立标准供应商产品接口 |
| 标准鉴权请求构造 | OpenAI 默认 `Authorization: Bearer`;Anthropic 默认 `x-api-key` 与版本头,不能混成一种鉴权 | 目前主要通过模板插件或调用方头部提供,需接成内置路径 |
| 统一消息、工具/图像等结构与流式事件 | 路由和中间件需要可靠输入,客户端不应各解析供应商流 | 现有消息以文本为主,Responses 会压平成字符串;工具/多模态保真需补齐 |
| 取消、超时、状态与结构化错误 | 插件和标准入口共用可靠执行路径 | 已有部分实现;要统一验证,不能把“部分”写成“全部” |
| 插件加载/版本/启停/隔离/能力接口 | 没有宿主,插件文件不会自行生效 | 已有供应商包运行时与安全解包;通用扩展注册与卸载仍缺 |
| 请求生命周期与策略调用入口 | Core 负责调用插件、验证插件结果、按最终选择执行 | 未形成完整管线;不同扩展点需要分别设计 |
| 原始 token usage 与请求事件 | 统计插件必须有事实输入 | 有部分 usage 解析;不等于账号余额查询或完整统计服务 |
| URL/头校验、凭据作用域和日志中的秘密清理 | 这是底座责任,不能因用户未安装“脱敏插件”而泄露 API Key | 有部分隔离/校验,新标准入口也要覆盖 |
| gomobile JSON 接口 | iOS 统一调用标准 API 与扩展能力 | 已有供应商插件桥和路由原型桥,标准 API 桥与扩展点待接 |

“Core 内置接口”指构造请求与解析响应。实际连接仍由 iOS 的 URLSession 提供;Keychain、登录页面、包存储、统计记录落盘与界面属于 iOS。Core 不新开网络连接,不保存用户密钥。API Key 接入不等于支持网站订阅账号或自动获得 OAuth 权限。

## 哪些 Magpie 能力通过插件提供

| 能力 | 插件负责 | Core/iOS 仍需提供 |
|---|---|---|
| 非标准供应商 | 自己的登录、刷新、模型/套餐查询、请求适配 | 隔离账号、Keychain 桥、网络与取消;请求走包自己的 loader/fetch |
| 路由 | 难度判断、成本/速度/期限/额度排序、权重与会话策略 | 候选与状态快照、执行时钟、能力约束、结果校验、执行与解释接口 |
| 用量 | 供应商剩余额度查询、窗口归一扩展、聚合/计费/提醒 | 每次请求的实际 usage 与事件、带来源和时间的状态、存储/UI;未知保持未知 |
| 内容脱敏 | 正文敏感信息识别、替换与响应还原算法 | 出站拦截与回程钩子、流式还原上下文;用户要求脱敏而插件不可用时不得直接明文发送 |
| 中间件 | 请求/响应加工、附加逻辑 | 钩子顺序、取消、异常隔离与权限边界 |
| 预算、工具、观察与页面 | 相应业务与插件 UI | 各类扩展接口与平台桥;逐类接入,不以“包已加载”代替兼容验收 |

供应商配额、单次 token usage、统计报表是三件事。可以把查询、分析和展示扩展插件化,但不能把标准响应已经给出的实际用量丢掉,再让插件猜。日志隐藏 API Key 与用户正文的可选脱敏也是两种不同职责。

## 需要避免的插件兼容误判

原版 Magpie 至少有两种不同的扩展方式:

- 可安装的 JS 供应商/网关扩展。参考源码已有 `strategies` 和 `onUsage` 等接口,可作为路由与统计兼容工作的起点。
- 原版编译入程序的 Go 插件模块。例如 `plugins/rotation` 注册路由策略,`plugins/redact` 注册内部 masker,并依赖原版服务。它们不是复制目录就能被 iOS 的 JS 加载器执行的包。

因此“路由、用量、脱敏装 Magpie 插件”这个分层可行,但对应原版模块未必已经有可直接安装的 iOS 兼容包。需要列出可原包运行、需宿主适配、需移植成插件的清单。Node/Bun/CLI 依赖在 iOS 上仍是明确能力缺口,插件化不会自动消除。

标准 OpenAI/Anthropic 调用不能只把目前的 `testdata/*-compatible` 模板打包进 App 冒充内置:它们可以做行为参考,但目标应是无需安装插件的第一方标准 API 路径。

## 对现有工作的处置

| 现有内容 | 建议 |
|---|---|
| `magpieplugin` 的包/模块/授权/流式基础 | 继续复用,与漫画插件隔离 |
| Chat/Responses/Messages 编码与解码 | 提取或复用为标准协议基础,补足结构化消息与事件 |
| OpenAI/Anthropic 模板 | 继续作为夹具/参考,不作为标准接口必须安装的产品包 |
| `magpierouting` / `PlanRoute` | 保留为原型,后续拆分底座检查与策略;不再当作插件兼容完成证据 |
| Swift 路由包装与策略存储任务 | 先核对已有补丁,不要继续扩大必经内置策略;插件接口明确后再接最终入口 |
| 模拟器 Copilot 验证 | 继续,验证非标准供应商插件、Keychain、登录与流式,不依赖桌面 Magpie |
| 桌面端 | 连接已安装 Magpie,保持与 iOS 实现路径独立 |

当前没有完成独立标准 API 内置入口、通用路由策略注册、脱敏中间件或完整用量观察管线。已有 Core 构建或 iOS 164 条测试的通过记录不能证明这些新边界已实现。

## 建议落地次序

1. 标准 API 独立路径:OpenAI Chat/Responses 与 Anthropic Messages,自定义 base URL、各自鉴权、流式/取消和错误;真实请求仍由 iOS 发送。
2. 统一标准调用与供应商插件的请求生命周期,保留原始事件/usage;先固定扩展点的输入输出和版本。
3. 接路由策略与用量查询/观察插件,验证跨供应商同名模型、多账号、未知额度、策略失败和显式选择。
4. 接内容脱敏的请求/响应管线,特别验证分块还原、失败时不外发及秘密不入日志。
5. 逐项接其他 Magpie 扩展,持续用固定版本原包验收。用户真实 Copilot 登录验证并行推进。

无扩展插件时的基线是“用户选定的标准账号和模型可直接调用”,不偷偷替用户启用到期优先、自动分类或敏感内容脱敏策略。

## 第一项实现契约:标准请求构造

拟新增 `aiapi` 包,先实现不联网的请求构造,后续再接执行与 gomobile。接口草案为 `BuildRequest(config, json.RawMessage)` 与 `BuildModelsRequest(config)`,返回 `host.Request` 或错误。该阶段不加载 JS 包、不安装模板、不调用路由原型。

- 协议明确区分 `chat`、`responses`、`messages`;默认分别使用 OpenAI `/v1/chat/completions`、`/v1/responses` 和 Anthropic `/v1/messages`。自定义 base URL 是 API 根路径,不自动猜测第三方需要的版本目录。
- OpenAI 用 Bearer Key;Anthropic 用 `x-api-key` 与版本头。空凭据或不合法 URL/头直接拒绝,错误不得带出 key;Core 不持久化凭据。
- 正文采用目标协议原生 JSON 对象,保留原始字节、字段顺序与精确数字。`messages`/`input`、工具、图片、推理和未知扩展字段不压平成文本,不伪称已经完成跨协议转换。
- 允许普通及流式请求,按原正文的 `stream` 选择;本阶段只构造请求,不声称已完成流式执行。模型目录请求单独构造 `GET /models`,不能假造成功的模型列表。
- 请求关闭自动 Cookie,附加头不能覆盖协议鉴权或伪造 Host/消息长度。URL 中的 userinfo、查询与 fragment 不作为放密钥的捷径。

iOS 网络桥仍需真实流式契约。此前 `mobileHost.Do` 缺请求 `id`、取消未透传,而 Swift `CoreHost.WireRequest` 要求 `id`。当前本地修复复用 `hostBridge.Do`,统一漫画与 Magpie 的 HTTP ID 分配,并透传 `ctx` 到 `CancelHTTP`;四条契约测试已验证必填 ID、跨桥唯一性、取消匹配与预取消不发请求,`go test -race ./mobile` 通过。此修复尚未发布或在 iOS 端验证,不表示真实账号登录已完成。

`mobileHost` 仍未实现 `Streamer`,Swift `URLSessionTransport.send` 仍等待完整正文。后续必须以“请求未结束时收到首块”和“取消后底层请求终止”的 iOS 端证据验收,不能用 SSE 解析或分批读取已缓冲事件代替实时流式验证。
