# 验证与证据

[English](VERIFICATION.en.md) | 简体中文

这份文档说明:**在这个项目里,「验证过」是什么意思**,以及怎么自己复核。写它是因为多次出现「看起来验过了」但实际没有:总数对得上而文件少了、框架落后于源码、传输把一段改写成长度相同的内容。

## 什么算证据

| 说法 | 需要的证据 |
|---|---|
| Go 代码能编译并测试 | `go vet ./...`、`go test -count=1 ./...`(涉及并发改动再加 `-race`) |
| Apple 侧能编译 | CI 的 Apple job:造 xcframework + macOS 与 iOS 模拟器的 Swift 冒烟测试 |
| 客户端的某个提交被验证过 | 那一份源码的逐文件清单与 CI/机器上的运行结果,**不是**「总数差不多」 |
| 某个供应商包能跑 | 用**该包本身**跑通:加载、登录、刷新、模型、用量、流式、取消;只加载成功不算 |

## 四个反复踩到的坑

1. **总数对得上不等于树相同。** 见过 `112 tests` 与 `114 tests` 两种说法都“合理”,而两份树都少了文件。判据应当是逐文件的:客户端用 `scripts/check-tree.sh`(给出 `shape` 摘要)与 `scripts/manifest.sh`(逐文件 md5);两边 `shape` 相同才说明同一批用例在同样的文件里。
2. **框架会落后于源码。** 源码调 `chatStart`、`Vendor` 里的框架却没有这个方法时,报错发生在 Swift 编译里,看上去像方法名写错。客户端因此在编译前先跑 `scripts/check-core-surface.sh`,并明确列出期望的 18 个选择器。
3. **传输会做等长改写。** 见过一段 base64 长度不变、内容变了,只有逐段 md5 能发现;整包 md5 只能告诉你“坏了”,不告诉你“坏在哪”。现在 Core 公开在 GitHub 上,能 `git clone` 就不该手搬。
4. **工具的入口不一定是环境变量。** 框架的 macOS 部署目标比客户端声明的新时,链接会报警;`export MACOSX_DEPLOYMENT_TARGET=26.0` 看起来像修好了,实际毫无作用 —— clang 认、纯 Go 的 cgo 也认,但 `gomobile` 只读自己的 `-macosversion` 旗标,从不看这个变量。写这类「看起来像修复」的改动时,要么在真机上验证它确实生效,要么在提交说明里写明未验证。

## 怎么复核一次

Core:

```sh
go vet ./... && go test -race -count=1 ./...
sh scripts/check-docs.sh
gh run list --limit 1        # Apple job 也在里面
```

客户端(需要在 macOS 上,Core 直接克隆):

```sh
scripts/fetch-core.sh        # 按 scripts/core-version 钉住的提交编译 xcframework
sh scripts/check-core-surface.sh
sh scripts/check-tree.sh
swift test
```

## 跨机器交付:让补丁自己证明

把改动送到另一台机器时,「删掉这两行、留一个空行」这种描述**无法被验证**:对方照做,md5 仍不同,只能再来一轮。这次就这么来回三轮。

可验证的做法是发**补丁**,而且发之前先在自己这边证明它能落到目标字节:

```sh
scripts/make-patch.sh BASE_DIR OUTDIR FILE...   # 客户端仓库里的工具
```

它以对方手里的旧副本为基准生成 `fix.patch`,把补丁应用到一份草稿副本上,逐文件比对 md5;对不上就失败,不会发出一个"大概对"的补丁。收方只需 `patch -p0 < fix.patch` 再比一次 md5。

判断「两棵树是否相同」也同理:**shape 摘要只证明用例分布,不证明字节**。真正闭环的标志是逐文件 md5 相同——客户端那次验证就是这样收尾的:13 个 Magpie 源文件加测试文件逐一比对,最后三个漂移的文件全部对齐。

## 机器没有凭据时怎么把代码送过去

验证机常常连不上私有仓库:没有 `gh`、没有 token、`~/.ssh` 里没有私钥。三种尝试(HTTPS、`gh`、SSH)都会失败,而且失败得很快——**不要在这上面反复试,也不要让验证机去生成密钥或改认证配置**,那是别人的机器和别人的账号。

可用的顺序:

1. 公开仓库直接 clone(本仓库就是);私有仓库不行就往下走;
2. `scripts/make-payload.sh` 打整包 → 放到 **secret gist** → 验证机 `curl` 取回。包里带归档 md5、base64 md5 与逐文件 md5,收方先验再解;
3. 两边都有树之后,只发补丁。

两条必须记住的细节:

- **gist 用完立刻删。** secret 只是「不列出」,拿到链接的人都能读,它不是仓库的替代品。
- **手抄哈希是错的那一环。** 一天里错了三次,每次都在消息里把一个 32 位哈希写歪。现在由 `scripts/make-transfer.sh` 从文件读值、直接打印整条可粘贴的消息;验证机也被告知「md5 不符就停下来报,不要自己对齐」。

还有一个容易把正常情况报成失败的地方:验证机 `fetch-core.sh` 会把 Core 克隆到 `build/` 下,而 Core 自带的 `apple/CoreSmoke` 有 `.swift` 文件。统计文件数的脚本如果不排除 `build/`,两台机器的数字就永远差 2。要么排除,要么在报告里解释——**默认应该排除**。

## 说清楚「没验到什么」

比多说一句更有用。例如客户端的那次验证:跑了 `swift test` 与 Swift 6 类型检查,但**没有**跑 `xcodebuild` 归档与签名,也没有 iOS 模拟器运行时;验证用的树不含 `project.yml`。这些写在客户端的 STATUS 里,因为读者会默认「验证过」覆盖了这些。
